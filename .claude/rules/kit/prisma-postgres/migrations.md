# Миграции

Как писать модели — `schema.md`.

## Как меняется схема

- Только миграцией: `npm run prisma:migrate -- --name <имя>`. Схема и папка миграции коммитятся вместе.
- `prisma db push` — только на своей локальной базе, чтобы попробовать.
- Имя миграции — по смыслу, на английском, snake_case, с глаголом: `add_invoice_state`, `drop_customer_legacy_code`.
- Слитая миграция не редактируется, не переименовывается и не удаляется. Исправление — новой миграцией. Обратных миграций нет.

## Есть ли пользователи

Разделы «Совместимость» и «Блокировки и данные» действуют, только когда у продукта есть пользователи: развёрнуто окружение с настоящими данными, которое нельзя остановить или пересоздать. Пока их нет, несовместимое изменение делается одной миграцией в одном выпуске.

Перед несовместимым изменением схемы — удалить, переименовать, сменить тип, сделать поле обязательным — агент спрашивает, есть ли пользователи. Ответ не предполагается и не берётся из прошлых задач: стадия проекта меняется. Текущая позиция записана в `docs/decisions.md`, «Исходные позиции».

Остальные разделы действуют всегда.

## Совместимость

Миграция выполняется до запуска новой версии, пока работает старая. Откат возвращает прошлый образ, но не схему. Поэтому миграция совместима с предыдущей версией приложения.

| Изменение | Выпуски |
| --- | --- |
| Новая таблица, необязательное поле | один |
| Удалить поле или таблицу | два: код перестаёт читать и писать; следующий выпуск удаляет |
| Переименовать поле или таблицу | три: добавить новое; перевести код; удалить старое |
| Сделать поле обязательным | два: заполнить и всегда писать; следующий выпуск ставит `NOT NULL` |
| Новое значение enum | два: сначала код умеет его читать; писать его начинают выпуском позже |

## Блокировки и данные

- Миграция короткая и не держит долгих блокировок.
- Индекс на существующей таблице — `CREATE INDEX CONCURRENTLY`, отдельной миграцией.
- Перенос данных — фоновое задание, а не миграция.

## Транзакция миграции

Prisma не оборачивает миграцию в транзакцию: упавшая на середине миграция оставляет всё, что успела сделать.

- Миграция из нескольких шагов, которые имеют смысл только вместе, сама пишет `BEGIN;` и `COMMIT;`.
- `CREATE INDEX CONCURRENTLY` в транзакции не работает — поэтому он в отдельной миграции.

## Проверяется автоматически

- `schema-migrations-sync`: `prisma migrate diff --exit-code` в CI.
- e2e применяет все миграции к чистой базе.

## Не проверяется

- Что перед несовместимым изменением спросили о пользователях.
- Совместимость с предыдущей версией и число выпусков.
- Что слитую миграцию не меняли; имена миграций.
- Транзакция у многошаговой миграции; длительность блокировок.
