# Транзакции и замки — `Transactions`

## Роль

- **Зачем.** Пределы времени транзакции заданы в одном месте, а транзакция видна в сигнатурах, а не подставляется незаметно.
- **Контракт.** Открывает транзакцию, отдаёт её в колбэк, фиксирует при успехе и откатывает при исключении, пропуская исключение наружу.
- **Где.** `src/shared/db`; тип транзакции — `Tx` там же.
- **Запрещено вне реализации:** `$transaction` клиента Prisma; библиотеки, которые подставляют транзакцию незаметно.

Транзакция передаётся явно — первым параметром `tx` в каждый вызов, который должен в неё попасть.

```ts
return this._transactions.run(async (tx) => {
    const invoice = await this._invoices.lockById(tx, invoiceId);
    invoice.void(this._clock.now());
    await this._invoices.save(tx, invoice);
    return invoice.view();
});
```

## Пределы времени

У транзакции два предела по 5 с:

1. **На каждый запрос.** Его держит сервер базы: запрос, который ждёт замка или идёт слишком долго, обрывается ошибкой.
2. **На всю транзакцию.** Его проверяет Prisma, и только между запросами. Запрос, вставший на замок, этот предел сам не остановит.

Следствия:

- Транзакция из нескольких медленных запросов может прожить почти вдвое дольше: запрос, начатый перед концом второго предела, идёт ещё до 5 с. Жёсткий предел на всю транзакцию есть в PostgreSQL начиная с версии 17.
- Если у сессии свой предел запроса строже — из адреса базы, роли или настроек базы, — действует он.
- Запрос вне транзакции этих пределов не получает.
- Работа, которой нужно больше времени, делится на шаги или уходит в задание.

## Что нельзя внутри транзакции

Внешние вызовы — SMS, push, хранилище, почта, HTTP — внутри транзакции не делаются.

## Замки

- **«Проверил — защитил».** Запись, по которой принимается решение, блокируется в той же транзакции.
- **По умолчанию — `FOR UPDATE`.** Если на запись ссылаются внешние ключи, а транзакция её не удаляет и ключ не меняет, — `FOR NO KEY UPDATE`: `FOR UPDATE` ждёт проверок внешних ключей из других транзакций, и два параллельных создания дочерних строк приводят к взаимной блокировке.
- **Запись, которую транзакция не меняет**, но по которой решает, держится `FOR SHARE` (`holdBy…`): он не даёт её изменить и не ставит читателей в очередь.
- **Запись, которую транзакция изменит**, сразу берётся замком на изменение. Взять `FOR SHARE`, а потом менять нельзя: две такие транзакции ждут друг друга, пока база не оборвёт одну.
- **Общая строка**, от которой зависят разные операции, во всех них берётся одним и тем же замком на изменение, даже если не меняется: `FOR SHARE` пропустит обе операции разом. Если операция берёт сначала свою запись, а потом общую строку, этот порядок называется в описании PR.
- **Условие «записи нет»** замком строки не защитить. Оно перечитывается в транзакции, а последствие гонки называется в описании PR.

## Проверяется автоматически

- `lint-roles`: `$transaction` вне `src/shared/db`.
- e2e роли: успешная работа сохраняется и возвращает результат; исключение откатывает всё и проходит наружу; запрос, ждущий замка дольше предела, обрывается и ничего не пишет; предел действует только внутри транзакции; более строгий предел сессии сохраняется.

## Не проверяется

- Внешний вызов внутри транзакции.
- Решение по незаблокированной записи; выбор вида замка.
- Что транзакция из нескольких запросов укладывается в предел.
