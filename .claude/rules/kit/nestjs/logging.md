# Журнал событий — `EventLogger`

## Роль

- **Зачем.** Один формат событий, без персональных данных и с id запроса в каждой записи.
- **Контракт.** Пишет событие с именем из реестра и полями заданного типа. Отдаёт id текущего запроса. Маскирует поля с секретными именами.
- **Где.** `src/shared/logging`, глобально, через конструктор. Библиотека журнала импортируется только там и в точках входа процесса.
- **Запрещено вне реализации:** `console.*`, логгер фреймворка, прямой импорт библиотеки журнала.

## Что пишется само

- Одна запись `http.request` в конце каждого запроса: `requestId`, `method`, шаблон маршрута (`/api/v1/invoices/:invoiceId`, а не реальный путь), `status`, `durationMs`, `userId`.
- Тело, query, заголовки и IP не пишутся. Проверка здоровья не пишется.
- Необработанная ошибка — запись `http.unhandled_error`: тип, код, стек. Текст сообщения ошибки не пишется никогда: библиотеки подставляют в него аргументы вызова.

## Что писать нельзя

Имена, телефоны, email, адреса; тексты пользователей; коды входа и подтверждения; имена и содержимое файлов; токены и ключи.
В полях события — только id, числа и значения enum.

## Как объявить и записать событие

- Имя — `<модуль>.<что_случилось>`: `invoices.invoice_voided`. Отдельного текстового сообщения нет: событие и есть сообщение.
- Событие объявляется в `application/<модуль>.log-events.ts` расширением общего реестра событий. Сервис импортирует этот файл.
- В файле должен быть `import` или `export {}`: иначе TypeScript прочитает его как новое объявление, а не расширение.
- Событие пишется в момент вызова, а не после фиксации транзакции. Если транзакция откатится, событие останется. Поэтому по журналу не делают выводов о данных.

```ts
export {};

declare module '../../../shared/logging/log-events.ts' {
    interface LogEvents {
        'invoices.invoice_voided': { invoiceId: string; customerId: string };
    }
}

this._events.info('invoices.invoice_voided', { invoiceId, customerId });
```

## Уровни

- `error` — ответ 500, упавшая фоновая задача.
- `warn` — требует внимания, но ничего не сломалось.
- `info` — завершённый запрос, доменное событие. Ответ 4xx — тоже `info`: ошибся клиент.
- `debug` — только локально.

## Id запроса

Клиент может прислать `X-Request-Id` с UUID. Если заголовка нет или в нём не UUID, сервер создаёт свой id. Id возвращается в заголовке ответа и в теле ошибки и попадает во все записи запроса. Модуль получает его у `EventLogger`.

## Маскировка

Перед записью значение поля, в имени которого есть `password`, `secret`, `salt`, `api_key`, `authorization`, `cookie` или которое кончается на `token`, заменяется на `[redacted]` — на глубине до восьми уровней.
Это страховка, а не разрешение класть такие поля в события.

## Проверяется автоматически

- `tsc`: неизвестное событие, лишнее поле, неверный тип поля.
- `lint-roles`: прямые импорты логгеров и `console`.
- e2e журнала: одна запись на запрос с шаблоном маршрута и без данных запроса; проверка здоровья не пишется; `X-Request-Id` принимается только как UUID и попадает в события и тело ошибки; 500 пишется без текста сообщения; поля с секретными именами маскируются.
- unit: маскировка на глубине.

## Не проверяется

- Персональные данные в поле с обычным именем: `phone: string` пройдёт и компилятор, и маскировку.
- Имена событий и выбор уровня.
