<!-- kit:begin id=base/where-truth -->
## Где правда

- **Что должен делать продукт** — требования проекта (docs/requirements/). Код требований не задаёт.
- **Как писать код** — `.claude/rules/`: `kit/` — правила kit, `project/` — дополнения проекта. Правило подгружается само, когда работа касается его путей.
- **Что решено об устройстве системы** — `docs/decisions.md`. Туда попадает только подтверждённое владельцем проекта.

Если код расходится с требованиями, правы требования. О расхождении сообщают владельцу, а не исправляют молча.
<!-- kit:end id=base/where-truth -->

<!-- kit:begin id=base/ask-first -->
## Сначала спросить

Агент останавливается и спрашивает владельца проекта, если:

- для ситуации нет правила — своё не придумывается, ответ становится правилом или решением `Р-N`;
- нужна новая runtime-зависимость (`dependencies.md`);
- изменение данных или контракта несовместимо с текущей версией;
- проверку не пройти, не отключив правило линта или тест.

Владелец проекта — coldmelnyk.
<!-- kit:end id=base/ask-first -->

<!-- kit:begin id=base/branches -->
## Ветки, коммиты и PR

- `main` — выпущенное, `dev` — следующий выпуск. Прямых коммитов в них нет.
- Задача — своя ветка от `dev` и PR в `dev`: `feature/<модуль>-<что>` для нового поведения, `fix/<модуль>-<что>` для невыпущенной ошибки.
- Ошибка в выпущенном — `hotfix/<что>` от `main`, PR в `main`, после слияния `main` вливается в `dev`.
- Выпуск — PR из `dev` в `main`.
- Одна ветка — одна задача. Находка по пути — отдельная ветка.
- Коммиты — Conventional Commits на английском, область — модуль: `feat(invoices): void an issued invoice`.
- PR — по шаблону `.github/pull_request_template.md`. Агент открывает PR, но не вливает его.
<!-- kit:end id=base/branches -->

<!-- kit:begin id=nestjs/map -->
## Карта `src/`

Зависимости идут в одну сторону: `app → modules → core → shared`.

- `app/` — сборка приложения, без логики;
- `modules/<модуль>/` — прикладные модули, друг от друга не зависят;
- `core/<модуль>/` — ядро, о прикладных модулях не знает;
- `shared/` — общее без предметной области;
- `generated/` — сгенерированный код, руками не правится.

В модуле до пяти слоёв: `domain/`, `ports/`, `application/`, `infrastructure/`, `presentation/` (`layers.md`).
<!-- kit:end id=nestjs/map -->

<!-- kit:begin id=nestjs/read-first -->
## Прежде чем начать — прочитать

Правило по `paths:` подгружается, когда агент читает подходящий файл. Новый модуль с нуля читать нечего, поэтому:

| Делаешь | Прочитай |
| --- | --- |
| новый модуль | `nestjs/modules.md`, `nestjs/layers.md`, `nestjs/ports.md` |
| эндпоинт | `nestjs/api.md`, `nestjs/errors.md` |
| работу с базой | `prisma-postgres/persistence.md`, `prisma-postgres/transactions.md` |
| изменение схемы | `prisma-postgres/schema.md`, `prisma-postgres/migrations.md` |
| время, id, случайность | `nestjs/roles.md` |
| тесты | `base/testing.md`, `nestjs/testing.md` |
<!-- kit:end id=nestjs/read-first -->

<!-- kit:begin id=nestjs/done -->
## Готово, когда

Проходят `npm run lint`, `npm run typecheck` и `npm test`. Если менялись API или база — ещё `npm run test:e2e`.
Сгенерированный конфиг линта руками не правится: меняется скрипт генерации, затем конфиг пересобирается.
<!-- kit:end id=nestjs/done -->

<!-- kit:begin id=nestjs/always -->
## Всегда

- Журнал — только через `EventLogger`. В полях событий — только id, числа и значения enum.
- Время — только из `Clock`, id — только из `Ids`. Id сущности, которую создаёт клиент, приходит в запросе.
- Секреты и персональные данные не попадают в журнал, ответы и подробности ошибок.
- Другой модуль импортируется только через его `index.ts`. Чужие таблицы в запросах запрещены.
- Всё, что модулю нужно снаружи, — порт в `ports/`. В `domain/` абстрактных классов для DI нет.
<!-- kit:end id=nestjs/always -->
